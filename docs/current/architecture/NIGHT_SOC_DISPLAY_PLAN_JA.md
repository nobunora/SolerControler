# 夜間SOCの計画と実績の表示契約

2026-10-17利用者承認。開始時刻欠損を04:00〜07:00へ置換する旧参考計算を退役する。
当日の表示入力では04時0%、実機は04:00:13に39%であり、均等配分が実制御を表していなかった。

## データ経路

計画生成 → 保存原本・時間別予測 → 事前生成bootstrap/history → HTTP API → dashboard。
夜間SOCは計画生成時の開始SOC、観測時刻、充電速度と時刻契約から保存する。
画面は保存値を描画し、充電量の均等配分や07時目標からの逆算で夜間SOCを作らない。
実制御の03時開始、目標到達停止、06:45監視終了、23/07の独立性は変更しない。

## 欠損・時刻・出典

- 計画は生成時点の予測として固定し、後から取得した実績で上書きしない。
- SOCの時刻は時間開始値。生成以前の夜間を後日の計算で当時の計画として埋めない。
- 開始SOC・時刻・速度が確認できない区間は計画未確定とする。実測0は有効な実績として独立表示する。
- 日中07〜23時の保存計画とそのピークを維持する。
- 計画の生成時刻・版と実績の観測時刻を区別し、異なる計画版を混ぜない。
- 既存の過去原本に夜間計画がなければ欠損を維持し、再予想で過去原本を置き換えない。

## 読取性能と受入

初期bootstrapは従来の1回、初期history要求0回を維持する。履歴は明示操作で取得する。
GETで原本アーカイブ取得やDB履歴走査を追加せず、既存の事前生成データへ計画値を含める。
変更はSOC系列と既存時間別データの追加値であり、同一payloadの重複転送はしない。
圧縮転送量は本番受入で測定し、推測値を合格証拠にしない。
既存historyの過去日を新モデルで自動改変しない。将来、明示的に過去データを訂正する場合は
既存の履歴再生成手順でhistoryを再構築し、bootstrapだけ更新して訂正を取り残さない。

対象回帰は実測0、入力欠損、保存夜間計画、計画/実績分離、早期目標到達、監視期限、
日中計画不変、初期要求数と履歴遅延取得。実機設定を変更しないforecast/dashboard scopeで反映する。

## 同日再発行と保存済み派生値の修復

### 2026-11-03 06→07時の表示接続

利用者の明示指示で、最新夜間計画の06時が欠け、保存済み夜間予測の06時と最新日中計画の07時が有効な場合だけ、独立した点線の接続segmentを描く。凡例と説明で別計画の接続と明示する。元の夜間系列・日中17点・原本と発行時刻は変更せず、単一計画に結合しない。実績・参考SOCは接続点に使わず、欠測を補間しない。0%は有効値として扱う。既存の初期要求数、追加DB読取0と歴史的な計画/実績分離を維持し、`test_dashboard_hourly_display.js`で両端・欠測・実績更新後の不変を検証する。

### 2026-11-03 保存済み夜間予測の独立表示

利用者承認により、最新予報に夜間SOC・系統充電量がない場合も、当時保存した予測を別系列で表示する。
既存のsnapshot読取り1回から、対象時刻以前に発行された完全24区間の保存原本を選び、各夜間時刻で最新の
有効SOC・系統充電量と発行時刻・版を`retained_forecast_*`として表示用データへ含める。
最新予報の`forecast_*`や原本、所有map、日中17点を変更しない。後日再計算した値で欠損を補わない。
最新系列と保存済み夜間系列は別々の点線、実績は実線とし、消費予測も実績で上書きしない。
既存snapshot queryを共用し、初期bootstrap/historyの要求数・追加DB query数は増やさない。
実績更新は指定日の保存DBだけに行い、その成功後にbootstrap/historyの指定日部分を保存DBから再生成する。
対象外の日は再計算せず、保存済みの値を保持する。未反映の別日更新や同時更新を検出したら停止し、全履歴再生成へ拡大しない。
既定は受付時点のJST当日で、過去日は日付を明示した場合だけ。受付後の日付跨ぎで対象日を変更しない。
画面の日付欄を変更していない場合はrequestの日付を省略し、サーバーの受付時JST当日を使う。開いたまま日付を跨いだ画面の初期値を過去日の明示指定として送らない。利用者が変更した日付だけを明示指定として保持する。
翌日初回の保存でlatest batteryの選択行が変わっても、全未指定日の元文書のrevisionが同じなら他日更新とは扱わない。表示原本の日付と取込日が異なる場合は取込日のcurrent-plan有無/版も固定し、新日の採用と公開が重なれば停止する。
指定日の変更許容は取込が所有する実績sample・日次実績/料金のcollectionだけとする。同じ指定日でも予測・設定・モデルのnative revisionが変われば公開しない。
月次集計は既存の近日日次bootstrapをhistoryより優先して結合する。古いhistoryで金額を巻き戻さず、未指定日の行自体は再生成しない。
表示生成失敗は実績保存成功と別記録し、実績取込みの自動再実行で回復しない。
実績SOCの新しい表示点は毎正時の観測値に限定する。07:30を07:00の計画値と同時刻扱いせず、正時欠測は補完しない。
旧artifactの時間内最終SOCは明示的にその旨をラベル表示し、保存原本や既存実績の時刻を変更しない。

夜間計画が未確定になった再発行では、前の版の夜間SOCを残さない。Firestoreの
`forecast_plans`の所有mapは親field maskで置換し、時間別SOC・充電量の欠損はnullとして保存する。
未知のtop-level field、日中計画、PV・消費量、保存原本とそのSHA/発行時刻は保持する。

既存の不一致は `scripts/repair_forecast_night_projection_from_env.ps1` の
`-Stage prepare -TargetDate <日付> -StatePath <artifacts内の新規JSON>` で対象と原本を固定する。
prepareは読取りのみ。原本、世代、PV/消費量、日中SOCの一致と、最大8文書の夜間派生値だけのpatchを確認する。
利用者の承認範囲で、返されたSHAを `-ReviewedStateSha256` に指定して同stateの`-Stage apply`を1回実行する。
書込は1回のbounded transactionで、所有mapを置換する。原本・非対象文書を含む27文書のnative読返しを必須とする。
結果不明時は同stateの`-Stage verify`だけを行い、applyを繰り返さない。旧監視source repairは別用途であり流用しない。

この修復は直近31日だけを許可する。修復後の通常forecast実行でrecent履歴・bootstrapを再生成し、
修復日と当日を含むbounded backend/original照合、browser受入を行う。31日外はこの入口で変更せず、
履歴の全面再生成手順を別途固定する。GETで追加のDB/原本走査を発生させない。
