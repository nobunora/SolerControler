## 4. A：SOCの時刻情報と監視予定

### 4.1 現行経路と最小変更箇所

`cloud_job._RunnerMonitorDevicePort.read_soc` → `soc_reading.read_soc_with_fallback` → KP-NET表示ページ → SOC parser → `SocReading` → `_monitor_partial_forced_and_stop` → `ForcedChargeCompletionEstimator`。

修正予定は[runtime/soc_reading.py](../../../app/runtime/soc_reading.py)、[KP-NET parser](../../../app/kpnet/realtime_soc_parser.py)、[推定器](../../../app/runtime/forced_charge_monitor.py)、[03監視](../../../app/runtime/cloud_job.py)とその直接テスト。時刻契約、23/07入口、運転モード書込みコードを変更しない。

### 4.2 時刻データと互換性

`SocReading`の既存4フィールドと4位置引数を維持する。既存`observed_at`の意味を黙って変更しない。末尾にデフォルト付きで次を追加する設計とする。

| 項目 | 値・意味 |
|---|---|
| `retrieved_at` | UTC aware datetimeまたはNone。HTTP応答取得時刻 |
| `measured_at` | UTC aware datetimeまたはNone。SOCと結びつく明示的な元測定時刻 |
| `measurement_id` | 応答にある非機密の測定更新番号。未取得ならNone |
| `measurement_time_source` | `page` / `api` / `unknown`。取得時刻をpageと偽装しない |

外部へ公開済みのnumeric getter `latest_realtime_soc_percent`はfloat/Noneの戻り値を維持する。構造化getterを別に追加し、numeric getterは同じ取得結果のvalueを返す互換wrapperにする。1回のpollで数値用と時刻用に同じページを二重取得しない。既存callback注入テストは時刻なしの`unknown`として継続できるようにする。

`read_soc_with_fallback`の既存keyword引数を削除しない。構造化callbackをoptional keywordとして追加し、指定時だけそちらを1回呼ぶ。未指定時は既存numeric callbackを1回呼ぶ。型・引数変更で既存のfake device portやlegacy re-exportを壊さない。

測定時刻parserは、実機応答でSOC値に対応すると確認した欄だけを採用する。ページ時計、ログイン時刻、CSVラベル、初回の値変化時刻を測定時刻とみなさない。日付・timezoneがない時刻を現在日に推測結合しない。未来時刻・解析不能時刻はunknown理由を記録する。現在ページで有効な測定欄が見つからなければ、`measured_at=None`のまま実装・検証できる。

### 4.3 監視推定の状態

推定器へoptionalの観測時刻/現在時刻を渡せる入口を追加する。既存`remaining_minutes`/`next_check_seconds`の呼出しは従来動作を維持する。新経路の最小状態は、最後の確認済み測定SOC・測定時刻・更新番号・推定速度・到達予定時刻とする。

`ETA = measured_at + (target_soc - measured_soc) / rate`。単位は速度が%/時なら秒へ変換する。現在SOCの参考値は`measured_soc + rate × elapsed_hours`を0〜100%へ制限する。これは測定値ではなく推定値としてのみ扱う。

同じ測定ID/測定時刻の再取得で基準時刻を新しくしない。SOCが同じでも元測定時刻が新しければ新測定として扱う。元測定時刻がunknownの場合は既存のSOC差による方式を維持し、推測したageを入力しない。単調時計をsleep/deadline、aware wall clockを測定年齢の計算に使う。

次回pollは既存の最小60秒・通常最大poll秒・06:45までの残時間へ制限する。ETAが過去でも、SOC未到達の値に対してdelay=0でbusy loop/推定停止を起こさず、許された最小pollで確認を続ける。時刻情報が得られない場合、前倒しを保証する機能とは報告しない。

既存confirm-before値は維持する。測定遅延・通信/停止操作時間を含む動的余裕は観測してログへ出す段階に限定し、根拠のない遅延上限や速度分位点を新しい本番定数へしない。実機の上限検証後に別途採用する。

### 4.4 停止と失敗の不変条件

- target reachedは従来どおり直接取得した数値SOCがtarget以上のときだけ。推定SOC・ETA・marginを停止条件にしない。
- 新しい時刻メタデータの解析失敗は、SOC数値取得の失敗へ変換しない。numeric値取得成功の通信失敗リセットを維持する。metadataの鮮度問題は別の診断として記録する。
- 古い時刻の測定値を停止判断から除外する仕様は、従来停止条件を変えるため今回のAへ含めない。鮮度判定だけを追加して、停止の保証が得られたとは扱わない。
- CSVの03制御代用禁止、連続通信失敗でstandby、06:45監視終了/06:50最終standby開始期限/06:55 I/O禁止を保持する。
- ログ項目追加は既存stdoutに限定。03へDB/Firestore・lease・再適用・owner依存を追加しない。

### 4.5 Aの受入条件

時刻あり/なし/解析不能/未来、同値の新測定/同測定反復、UTC/JST跨ぎ、ETA過去、速度異常、通信単発失敗/連続失敗、時刻境界をテスト。既存4位置引数・numeric getterの互換性、数値と時刻の解析を同じ応答から行い追加ページ取得が0回であること、100%目標で99%停止しないことを検証。認証redirect等の既存要求数とメタデータ取得用の追加要求数を区別する。実機時刻欄の取得は未確認なら`NOT VERIFIED`と記録する。

## 5. B：最終予測の前日残差補正（ローカル候補）

### 5.1 境界と候補方式

既存`correction_model.calculate_forecast_correction`の物理残差・快適性モデルを適用した系列を比較基準とする。生の物理PVへ日計EWMAを重ね掛けしない。既存のproduction補正やshadow selectorの候補集合・21日/2% policyは変更しない。

最初の実装は独立したオフライン評価スクリプト。入力は保存forecast snapshot、先行修正込みの再生系列、同日同時間の実績。stdout/ローカルartifact以外を出力せず、production計画への接続なし。新補正候補を既存の凍結済みshadow policyへ混入させない。

同じ学習対象モデルの「条件別/快適性補正後・新EWMA前」の値を`q[d,h]`として保存。`e[d,h] = actual[d,h] - q[d,h]`を計算する。翌日の候補は`max(0, q[t,h] + b[t-1,h])`。最初は既存PV alpha=0.2、load alpha=0.5に相当する固定候補で比較し、値は実効設定から明示取得してfreezeする。

適格な実績が到着した日にだけ`b[d,h] = (1-alpha) * b[prev,h] + alpha * e[d,h]`を更新する。最初の適格残差を初期値とする。欠損日はstateを更新しない。alpha=0/1・非有限値の扱いを明示する。補正後の値からさらに同じ残差を計算して二重学習しない。

初期検証候補は時間別加算補正のみ。倍率補正・daypart分類・自動alpha選択・analog置換を同時に実装しない。供給能力の上限を新たに発明せず、既存の有効な上限が入力されている場合だけ適用する。極端な残差は件数と値を診断し、恣意的に削除しない。

### 5.2 データ品質・保存

日付×時間の両30分区間、有限のPV/load、発行時刻、モデル/入力version、補正適用順を確認する。実測0は有効。途中時間・欠損を完全な日計として更新しない。対象日より後に判明した値を対象日の推定に使わない。

新しいbaselineの`q`を保存していなかった期間は、厳密な状態更新に使わない。古い不具合込みのfinal forecastから`q`を逆算できると仮定しない。オフライン再構成は`reconstructed`、事前凍結値は`prospective`として区別する。モデル/補正仕様変更ではstateを分離する。

ローカルJSON/CSV項目はschema version、target date/hour、issue time、baseline version、q、補正state、最終候補、actual、適格/除外理由、更新時刻。read-onlyの既存snapshot読込を再利用し、production forecast_hourlyの書換え・DB schema変更は初期実装で行わない。

### 5.3 Bの受入条件

production出力不変、欠損/実測0/途中日/同日後発予報/モデル変更のテスト。日付・時間が完全一致する評価だけを用い、30日枠の評価日数・時間数・欠損理由を報告する。MAE/RMSE/bias、連続過小予測、既存SOCモデルによる購入費用差を比較する。

30日枠のオフライン再生と、最低30暦日の事前凍結prospective収集は別の条件。23日しか評価できない結果を30日合格としない。悪化した日も残す。補正の本番採用はこの比較後の別指示を必要とする。

## 6. C：SOC判断学習の更新経路（ローカル先行）

### 6.1 最小実装

既存`build_soc_decision_prior`と`evaluate_soc_candidate`を再利用する。予測時の選択と実績による採点に同じ費用関数を使い、月次・ピーク・売電の項目を一致させる。旧`build_soc_decision_feedback`の近似費用を新しい比較器へ混在させない。`persist_previous_day_soc_feedback`の03呼出しを戻さない。オフライン日次評価スクリプトが保存計画と完了実績を受け取り、学習なし/ありの選択SOC・採点・候補別regretをローカルJSONへ出力する。

比較器は既存SOCモデルの1時間・出力制限なしの近似として明記する。現在SOCと明示された夜間放電から得られる朝エネルギーより低い候補を、充電のみで到達可能としない。終了時の残量と明示単価による残量価値を出力し、単価ゼロの感度比較を行う。日別に保存初期SOC・月次料金状態へ条件付けた合計を、連続した実請求の再現と呼ばない。実機モデルの精度改善は別段階で設計する。

学習入力は対象日・issue time・decision time、計画時間07〜22時を全て含むPV/load、選択SOC、SOC now、有効容量、効率、cost model全項目、制約、候補grid、明示ピーク方針/単価、確率合計1のシナリオ、残量価値単価、model/contract/price version。16/18時間の物理PV出力を24時間必須として拒否しない。入力は全てサイト時刻で整合し、issue <= decision < 当日07時とする。数値項目の存在だけでなく有限性・範囲を検証する。ピーク不足量0/費用0から単価を推測せず、無効方針を既定値で復活させない。実績は別途48区間の完全性を検証する。

旧保存計画を正規化する場合は`reconstructed_experiment`と記録する。保存されたreserve/capと明示stepで候補を再構成し、候補数と保存候補要約の所属を確認する。欠落した旧projection flagは明示的な実験条件とし、採用来歴を作らない。料金/方針の変更で学習stateを分離する。日ごとに変わる効率・月次累計は入力状態であり、毎日異なる契約versionにしない。予測時点の特徴を類似度評価へ渡し、当日実績はSOC選択後の採点と翌日以降の学習だけに使う。

更新は同じdecision id+実績versionで冪等。実績が訂正された場合は該当日の出力と依存する後続stateを再計算する。元入力と旧結果を保存し、遡及再計算を事前判断と偽装しない。

### 6.2 未保存03計画の扱い

02:35の保存計画を03の採用計画とみなさない。03実行に完全入力がない日は`plan_missing`として学習せず、過去の8/28文書を最近の結果へ書換えない。

### 6.4 ローカル誤差シナリオ再校正（2026-10-03）

`local_scenarios.recalibrate_scenarios`は対象日より前の同日PV/loadの組から候補ごとの倍率シナリオを作る。今回の固定実験は14暦日窓、倍率1のprior重み5、既存SOCモデルと同じPV倍率上限3。baseline/0.5倍/1倍の各過去予測を分母に使い、全候補で同じ学習日を使う。実測0は有効、欠損・非有限実績や非正の予測分母は理由付きで除外し、対象日・未来の実績は参照しない。履歴なしはpriorのみと明記する。経済評価に単価が不足する日でも、完全な予測・実績があるならシナリオ校正の適格性を別に判定する。

料金モデル費用と月次・ピーク・売電の方針費用は独立に報告する。既に閲覧した期間で係数を再調整して採用せず、候補と条件を固定して将来の完全な意思決定入力で検証する。過去のみを使う時系列再生と、候補決定後の未使用期間での検証を区別する。ローカル再校正は本番シナリオ選択や既存shadow policyを変更しない。

## 7. D：売電と経済評価の監査

最小変更は入力・内訳の照合テストとローカル費用報告。`soc_cost_model_from_env`、`SocCostModel`、最適化の数式、デプロイ設定は変更しない。

現在のinactive+neutral+売電単価0を保つ。契約がactiveと確認されれば既存revenue経路を使う候補を別比較するが、現在の契約を推測して変更しない。penaltyは既存の非金銭的売電回避方針としてのみ表示し、実際の請求額と同一視しない。

報告は夜間買電、日中段階買電、売電収入/売電policy費用、ピーク不足、月次policy、学習priorを別項目で示す。実支出に相当する部分と既存policyを含むtotal objectiveを分ける。「料金のみの最小」と「現行objectiveの最小」を混同しない。

夜間充電費用と売電policy費用の両方が含まれる場合、同じ損失を重複評価していないか候補別に報告する。劣化費用や損失を新係数へ加える変更は、根拠と別仕様が得られるまで行わない。`541cd60`の前検針期間投影と生CSV buy/sell→費用のE2E契約を維持する。

受入テスト：inactive+neutralは売電費用0、penaltyはpolicy費用として非負、active+revenueは収入控除、未確認契約/単価不整合は既存validationで拒否。買電増が費用減にならないこと、元データ非0を集計0にしないことを確認。例示39.10/28.85を固定料金として実装せず、計画保存値を使う。
